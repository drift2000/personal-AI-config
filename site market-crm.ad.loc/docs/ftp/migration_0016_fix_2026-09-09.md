# Fix: `ftp.0016` broke fresh database builds

**Date:** 2026-09-09
**File changed:** `src/backend/ftp/migrations/0016_usersonedrive_remove_usersod_company_and_more.py`
**Type:** Bug fix (migration operation reorder, no schema/content change)

## Symptom

Building a database from scratch — a fresh test run, a new dev environment,
CI — failed at `ftp.0016` with:

```
django.db.utils.ProgrammingError: relation "users_onedrive" already exists
```

Reproduced on `main`/`develop` state prior to this fix via
`python manage.py test client` (any app's test run triggers the same full
migration replay). Discovered while trying to run tests for the new
`auth_azure` app (see `docs/auth_azure/README.md`).

## Root cause

`ftp.0014_usersod` creates model `UsersOD` with `db_table="users_onedrive"`.
`ftp.0016` renames it (in effect) to `UsersOneDrive`, keeping the same
`db_table`. Django's migration autodetector doesn't track `db_table` as a
dependency between models, so it generated `0016`'s operations in autodetect
order: `CreateModel(UsersOneDrive)` *first*, then the `RemoveField`s on
`UsersOD` and `DeleteModel(UsersOD)` *last`. Replayed literally, step 1 tries
to create a table that step "last" hasn't dropped yet — the old `UsersOD`
table (same name) is still there from `0014`.

This is a generated-migration ordering bug, not a data-model bug: the
*intended* end state (one `users_onedrive` table shaped like `UsersOneDrive`)
was always correct, and matches what's actually in the long-lived dev
database today (verified via `\d users_onedrive` before making this change)
— that database was migrated incrementally over real history and never hit
the ordering conflict, which only manifests on a from-scratch replay.

## Fix

Reordered `0016`'s operations — content is byte-for-byte identical, only the
sequence changed — so the old table is dropped before the new one is
created:

1. `RemoveField(usersod.company)`, `RemoveField(usersod.company_contact)`,
   `RemoveField(usersod.customer_contact)`
2. `DeleteModel(UsersOD)` — drops the old `users_onedrive` table
3. `CreateModel(UsersOneDrive)` — creates the new `users_onedrive` table
4. `AddField(userss3.collection)`, `AddField(userss3.type_input)`
5. `DeleteModel(AggregatedFTPUserData)`

(1) and (2) were already in that relative order in the original file; only
(3) moved from first to third.

## Why this is safe

- **No databases that already have `0016` applied are affected.** Django
  only replays a migration's operations when it isn't yet recorded in
  `django_migrations` for that database. Editing the file doesn't retroactively
  re-run anything on a database where the row is already there.
- **The end state is unchanged** — same models, same fields, same
  `db_table`, same final schema. Verified by diffing the operations list
  before/after: same 8 operations, same parameters, different order.
- **Verified against a truly fresh database**: dropped `test_enamine_db` and
  ran `python manage.py test` from scratch — all 20 `ftp` migrations
  (including `0016`) now apply cleanly, `python manage.py test client` and
  `python manage.py test auth_azure` both run (45 tests; only 2 pre-existing,
  unrelated failures remain — see below).

## Pre-existing, unrelated failures now visible

With the database able to build at all, two pre-existing failures in
`client.tests.MailchimpRequestTests` are now reachable (they were never
reached before because the suite always crashed at DB setup):
`test_request_uses_short_default_timeout` and `test_request_retries_on_timeout`
both fail because `MAILCHIMP_REQUEST_TIMEOUT` in this environment's `.env`
is set to `25`, not the test's hardcoded expectation of `5` — a
pre-existing test/env coupling issue in `client`, untouched by this fix.
Not fixed here (out of scope — flagging for a separate pass).
