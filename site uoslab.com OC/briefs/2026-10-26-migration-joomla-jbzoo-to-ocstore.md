# План міграції: Joomla 3 + JBZoo → ocStore 3.0.5.1 (PHP 8.3)

## Контекст

Магазин (~10к товарів, багато полів, змішаний продаж: частина товарів із цінами, частина «під запит») переїжджає з Joomla 3 + JBZoo (PHP 5.6) на ocStore 3.0.5.1 (`src/`, Docker-шаблон із `docker/`, PHP 8.3 за замовчуванням). Інші мови зараз — **окремі магазини** (окремі сайти Joomla) з неповним асортиментом. Локально наразі лише порожня БД `opencart`. Джерело — **старий бекап AkeebaBackup** основного магазину: для розробки цього достатньо, перед переходом знадобиться свіжий бекап.

**Ціль:** мульти-стор OpenCart. Store 0 — повний магазин українською та російською; окремі store — урізані магазини іншими мовами (див. «Цільова модель»).
**Фаза 1:** store 0, одна, основна мова. Переносимо категорії, товари з полями, зображення, статті/сторінки, відгуки, SEO-URL + 301-редіректи.
**Фаза 1b / 2:** друга мова store 0, потім урізані магазини.
**Що не переносимо:** клієнтів і замовлення (див. «Слабкі місця»).
**Режим:** ідемпотентний скрипт, який можна запускати повторно; розробка на старому бекапі, у день X — фінальний прогін на свіжому бекапі й перемикання.

## Архітектура інструмента міграції

- **Джерело (Akeeba):** архів `.jpa` (або `.jps`, якщо зашифрований) розпаковуємо через Akeeba Kickstart у PHP-контейнері в окремий каталог у `data/` (gitignored). Сайт через ANGIE не відновлюємо: беремо `installation/sql/site.sql` (+ частини `site.s01`, `site.s02`… якщо дамп розбитий), замінюємо плейсхолдер префікса `#__` на реальний і імпортуємо в **окрему БД `joomla_src`** у тому самому контейнері MariaDB (лише читання). З того ж архіву беремо `images/` і `media/zoo/applications/*/types/*.config`. **Важливо:** у ZOO/JBZoo визначення полів (назви, типи елементів) лежать у файлах, а не в БД; у `#__zoo_item.elements` є лише JSON зі значеннями за UUID елементів. Akeeba включає ці файли в бекап, тому достатньо одного архіву.
- **Розбіжність бекапу з живим сайтом:** нові поля чи типи, що з'явилися після бекапу, аудит на свіжому бекапі покаже як «не замаплені». Скрипт у такому разі не мовчить, а падає зі списком полів.
- **Інструмент:** PHP 8.3 CLI-скрипт у контейнері `php-fpm` (стек проєкту, той самий PHP, без нових залежностей). Він живе в окремому каталозі `migration/` поза `src/`, щоб не потрапити в прод-збірку. Пише безпосередньо в таблиці OC через PDO і транзакції: для 10к товарів це швидше й контрольованіше за API або CSV-імпортери.
- **Ідемпотентність:** службова таблиця `migration_map(source, entity, src_id, oc_id, hash)`. Поле `source` (код магазину-джерела) додаємо одразу, щоб у фазі 2 підключити інші магазини без переробки. Повторний запуск оновлює змінені записи (за хешем) і не створює дублікатів.
- **Конфіг мапінгу полів** (`migration/config/fields.php`): кожне поле JBZoo отримує ціль: `product column | attribute | filter | attribute+filter | option | extra | drop`. Конфіг генерується з аудиту, а потім правиться вручну.
- **Етапи як окремі команди** (`php migrate.php audit|categories|products|images|seo|content|reviews|verify`), щоб можна було перезапустити один етап.

## Етапи

### 0. Підготовка
- Розпакувати бекап Akeeba й відновити SQL у `joomla_src`, як описано вище. Архів, SQL і зображення — у `data/` (gitignored), не в репозиторій.
- Перевірити ocStore 3.0.5.1 на PHP 8.3: `display_errors` + E_DEPRECATED, прогнати адмінку й вітрину. Модулі під ionCube мають бути закодовані під 8.3. **Це ризик №1, перевірити першим.** Якщо щось ламається — тимчасово використати 8.2 з `docker/php-fpm/`.
- В ocStore лишається одна мова — мова основного магазину.

### 1. Аудит даних (ключовий етап, без нього мапінг робиться наосліп)
Команда `audit` формує CSV-звіти:
- версія JBZoo (за наявністю таблиць `#__zoo_*`, `#__jbzoo_*`), застосунки, типи;
- **інвентар полів:** тип → елемент (UUID, назва, тип елемента) → % заповненості, кількість унікальних значень, приклади значень, мова;
- який ключ однозначно ідентифікує товар (артикул/SKU): він знадобиться у фазі 2, щоб зіставити товари з інших магазинів;
- товари без ціни, дублікати SKU/alias, «биті» посилання на зображення.

**Результат:** таблиця рішень по кожному полю, яку погоджуємо разом. Евристика:
- ціна, артикул, вага, кількість → колонки `oc_product`;
- характеристики для показу → **атрибути** (`oc_attribute_group`/`oc_attribute`/`oc_product_attribute`);
- поля для фільтрації з невеликою кількістю дискретних значень → **ще й фільтри** (`oc_filter_group`/`oc_filter`/`oc_product_filter` + `oc_category_filter`);
- поля з заповненістю <5% або дублюючі → кандидати на видалення;
- файли, документи, зв'язки → `oc_product_related`, завантаження (`oc_download`) або окрема таблиця `oc_product_extra` (рішення після аудиту).

### 2. Імпорт (порядок важливий через залежності)
1. **Категорії:** дерево, `oc_category_path`, описи для всіх мов, `oc_category_to_store`.
2. **Довідники:** групи атрибутів, атрибути, групи фільтрів і значення фільтрів (нормалізація: обрізати пробіли, уніфікувати регістр та одиниці виміру).
3. **Товари:** `oc_product`, `oc_product_description` для кожної мови, `oc_product_to_category`, `oc_product_to_store`, атрибути, фільтри. Товари «під запит»: ціна 0 + прапорець (окрема колонка або значення в `extra`), який шаблон вітрини показує як «Ціна за запитом» замість кнопки «Купити». Це невелика правка twig або OCMOD.
4. **Зображення:** копіювання в `image/catalog/products/<id>/`, нормалізація імен (транслітерація, нижній регістр), дедуплікація за хешем, головне зображення → `oc_product.image`, решта → `oc_product_image`. Звіт про відсутні файли.
5. **Пов'язані товари.**
6. **Статті й сторінки** (`#__content`) → `oc_information` (+ описи, SEO). Посилання всередині HTML переписуються на нові URL (`index.php?option=com_zoo...` та старі alias).
7. **Відгуки** (коментарі ZOO або відгуки JBZoo, залежно від аудиту) → `oc_review` (прив'язка через `migration_map`, рейтинг і статус зберігаються).
8. **SEO-URL:** `oc_seo_url` для кожної мови; за можливості зберегти старі alias; розв'язати колізії (у межах store+language keyword має бути унікальним).

### 3. 301-редіректи
- Список старих URL беремо з трьох джерел: з sitemap старого сайту, з роутингу JBZoo/Joomla (генерація URL з alias категорій і товарів) і зі сторінок у Search Console/логах.
- Генеруємо nginx `map $request_uri $new_uri` в окремий include-файл поруч із `docker/nginx/default.conf`. 10к записів для `map` — нормальний обсяг: працює швидше, ніж модуль редіректів у PHP.
- Скрипт перевірки: кожен старий URL → 301 → 200 на новому сайті.

### 4. Верифікація (команда `verify`)
- Звірка кількостей: категорії, товари, зображення, відгуки, сторінки (за мовами).
- Вибірка ~50 випадкових товарів: порівняння «старий/новий» за ціною, атрибутами, зображеннями, текстом.
- Для кожної мови: товари без опису, без зображення, без категорії.
- Фільтри: кількість товарів на значення фільтра має збігатися з даними JBZoo.

### 5. Репетиції та перехід
- 2–3 повні прогони на dev; заміряти час (орієнтир: хвилини, а не години).
- День X: заморозка редагування на старому сайті → свіжий дамп → повний прогін → `verify` → перевірка редіректів → перемикання DNS/vhost → sitemap у Search Console → кілька днів моніторингу 404 у `data/logs/nginx` і дописування редіректів.
- Старий сайт і його дамп зберігаються в архіві не менше кількох місяців (там клієнти й замовлення).

## Слабкі місця запиту і як я пропоную їх закрити
1. **«Багато полів» не означає «перенести всі 1:1».** Зазвичай 30–50% полів JBZoo порожні або дублюються. Аудит із погодженням таблиці рішень — обов'язковий етап, а не формальність.
2. **Клієнти й замовлення не переносяться.** Паролі Joomla (bcrypt) несумісні з OC 3 (sha1+salt), але сам перенос можливий: клієнтам потрібно буде скинути пароль. Варто окремо вирішити, чи потрібна історія для покупців, які повертаються. Якщо ні — зберегти дамп в архіві.
3. **OC 3 на PHP 8.3** — гілка 3.x офіційно не орієнтувалася на 8.3. Якщо проєкт довгостроковий, варто подумати про OpenCart 4. Зараз пропоную перевірити сумісність на етапі 0, а не відкладати.
4. **Фільтрація на 10к товарів:** стандартні фільтри OC прості (без діапазонів і лічильників). Якщо в каталозі потрібні діапазони чи числові фільтри, модуль фільтра треба обрати **до** імпорту, бо від цього залежить цільова модель даних.
5. **Старий бекап:** для розробки підходить, але фінальний прогін — лише на свіжому бекапі. Ціни, наявність і нові товари могли змінитися, навіть якщо структура та сама.
6. **Мульти-стор: у OC мови глобальні, а не прив'язані до магазину.** Кожна мова, увімкнена в системі, доступна в усіх магазинах. Тому знадобиться невелика доробка (OCMOD/event): для кожного магазину зберігати список дозволених мов, у перемикачі показувати тільки їх, а на чужу мову робити редірект. Мову за замовчуванням для магазину OC налаштовує штатно (`config_language` у `oc_setting` для `store_id`). Доробка невелика, але закладаємо її в план.

## Цільова модель: мульти-стор (рішення прийнято)
- **Store 0 — повний магазин, UA + RU.** Повний асортимент, обидві мови.
- **Store 1..N — урізані магазини іншими мовами.** Кожен на своєму домені чи піддомені, зі своєю мовою та своїм асортиментом.
- **Асортимент магазину** задається штатно через `oc_product_to_store`, `oc_category_to_store` і `oc_information_to_store`. Один товар — це один `product_id` з описами всіма мовами, а магазини лише показують його або не показують. Так немає дублювання товарів, і ціна та наявність спільні.
- **SEO-URL** штатно розділені за `store_id` + `language_id` у `oc_seo_url`, тож редіректи робимо окремо для кожного домену.
- **Мова всіх магазинів однакова в адмінці**, тому описи товарів однією мовою вводяться один раз.
- **Обмеження, які треба врахувати:** ціни й валюти в OC спільні для всіх магазинів (у кожного можна задати лише валюту за замовчуванням). Якщо в урізаних магазинах ціни інші, це окреме завдання, тож варто з'ясувати заздалегідь.

## Відкриті питання
- **Окремі ціни в урізаних магазинах:** поки невідомо. На фазу 1 не впливає. Аудит фази 2 порівняє ціни за SKU між магазинами й покаже, чи є розбіжності. Якщо є, рішення ухвалимо тоді.

## Порядок фаз
1. **Фаза 1 — store 0, основна мова** (етапи 0–5 вище, але без перемикання DNS).
2. **Фаза 1b — друга мова store 0 (UA/RU).** Зараз UA і RU — два окремі сайти на Joomla, тому працюємо з окремим бекапом за тією ж механікою, що й у фазі 2: зіставляємо товари за SKU й додаємо переклади до тих самих `product_id` у store 0. Для фази 1 беремо магазин із повнішим асортиментом. Товари, які є тільки в другому магазині, створюємо як нові. Розбіжності між двома магазинами (у цінах, категоріях, наборі полів) винесемо в окремий звіт. Якщо значення в магазинах розходяться, для store 0 джерелом істини вважаємо магазин із фази 1.
3. **Фаза 2 — урізані магазини.** Для кожного: бекап → `joomla_src_<code>` → аудит (поля можуть відрізнятися) → зіставлення з уже імпортованими товарами за SKU (звіт: зіставлено / не знайдено / конфлікти) → створення store в OC → додавання перекладів категорій, товарів, атрибутів і сторінок → записи `*_to_store` тільки для товарів цього магазину → SEO-URL і редіректи для його домену. Товари, яких немає в store 0, імпортуються як нові та прив'язуються лише до свого магазину.
4. **Перехід** можна робити або для всіх магазинів одразу, або поетапно (спочатку store 0). Поетапний варіант безпечніший: старі урізані сайти працюють, доки їх не перенесено.

## Критичні файли
- `migration/` (новий; CLI-скрипт, конфіг мапінгу, звіти) — поза `src/`
- `docker/nginx/default.conf` + новий include з `map` редіректів
- `docker/scripts/restore_db.sh` — використати як основу для відновлення `joomla_src`
- Шаблон картки товару в `src/catalog/view/theme/*/template/product/` — «ціна за запитом» і показ extra-полів

## Наступний крок після погодження
Отримати архів Akeeba (і пароль, якщо це `.jps`), запустити етап 0 та аудит (етап 1), принести вам таблицю рішень по полях. Опційно: завести приватний каталог проєкту (`private-project-memory`), щоб зберігати там рішення щодо мапінгу.
