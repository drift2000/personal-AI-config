Мета
----
Підтримка імпорту регулювань, версіонування документів і дозаповнення (enrichment) даних для проєкту "Chem Regulations".

Область застосування
--------------------
- Імпортні парсери і трансформації даних з різних джерел (файли, сайти).
- Логіка імпорту: створення/оновлення `Regulation`, `RegulationDocumentVersion`, зв'язок з речовинами.
- Enrichment: додаткові запити у зовнішні сервіси (наприклад PubChem) для доповнення метаданих.
- Тести для парсерів і імпорту.

Технологічні вимоги
-------------------
- Довідковий стек: Django 4.x, PostgreSQL.
- Код має слідувати стилю та структурі існуючого репозиторію.

Ключові правила та практики
---------------------------
- Парсери повинні бути модульними, тестованими і ідемпотентними.
- Під час розробки зберігати оригінальні файли локально/на об'ємі, але не додавати їх у git.
- Скачані файли регулювань зберігати у папці `catalog/` (workspace-local), з чіткою позначкою версії.
- Дедублікація речовин — за `InChIKey` (обов'язково). `CAS` — допоміжний ідентифікатор.
- Версіонування документів:
  - Зберігати: шлях до файлу, контрольний хеш (SHA256), номер версії (v1, v2...), період дії, джерело, хто завантажив, позначка актуальності.
  - Якщо хеш не змінився — не створювати нову версію.
- Не видаляти історію: замість видалення оновлювати статус (`Active`, `Removed`, `Suspended`).
- Enrichment має бути окремим, замінним модулем/скриптом, який можна викликати або відключити.
- Має бути логування операцій імпорту з метриками: кількість створених/оновлених/позначених як видалені записів і помилок.

Рекомендована модель даних (коротко)
----------------------------------
- `Regulation`: назва, країна (ISO 3166-1 alpha-2 або 'EU'/'UN'), тип (Import Ban/Export Ban/Restricted/Precursor Control/Scheduled Substance/Other), document_number, коментар, дата створення.
- `RegulationDocumentVersion`: FK->Regulation, версія, шлях до збереженого файлу, хеш, дата дії (з/по), is_current, source_url, uploaded_by, notes.
- `Substance`: name, InChIKey, parent_substance (nullable FK), status (needs_review/validated), extra JSON.
- `SubstanceInRegulation`: FK->Substance, FK->RegulationDocumentVersion (або Regulation), restriction_type, date_from/date_to, status, removed_at, details, extra JSON.
- `Synonym`: FK->Substance, synonym_type, value, source.
- `Structure`: FK->Substance, SMILES, SMARTS, mol_weight, formula, structure_type, validation_status, notes.

Імпортний процес — шаблон
------------------------
1. Завантаження/збереження файлу (розробка: save locally into `catalog/`).
2. Парсинг: нормалізація назв, вилучення метаданих, структури, синонімів; виділення уявлення речовини для дедублікації (InChIKey).
3. Перевірка змін: обчислити SHA256 файлу/джерела; якщо хеш ідентичний — зупинитися.
4. Транзакційний імпорт у БД: створити/оновити `Regulation`, додати `RegulationDocumentVersion`, синхронізувати зв'язки з `Substance` (створити нові або оновити існуючі за InChIKey).
5. Встановити статуси речовин у контексті регулювання (`Active`/`Removed`/`Suspended`) замість видалення.
6. Виклик опціонального enrichment-модуля для доповнення CAS/синонімів/структур.
7. Логування підсумків: counts, errors, created_versions, updated_substances.

Тестування
---------
- Юніт тести для парсерів (різні приклади вхідних файлів).
- Інтеграційні тести для імпорту (тестові fixtures для БД).
- Тести на ідемпотентність (повторний імпорт одного й того ж файлу не змінює дані).

Операційні нотатки
------------------
- На етапі розробки імпорти — ручні; автоматичні оновлення плануються на другому етапі.
- Доступ до збережених файлів у `catalog/` має бути керований поза git (volume, артефакт, або локальна папка).
- При сумнівах щодо ідентифікації речовини — питати джерело і приклади рядків з файлу; документувати парсер.
