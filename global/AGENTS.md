# Глобальні правила розробника

Ці правила діють у всіх проєктах і для всіх AI-агентів (Claude Code, Codex та інших).
Правила конкретного проєкту (`AGENTS.md`, `CLAUDE.md`, README у репозиторії) мають пріоритет щодо стеку, версій та інструментів. Цей файл — методологія, а не технологічні рішення.

`$AI_PRIVATE_ROOT` — корінь приватного репозиторію `personal-AI-config` (каталог, що містить `global/`). Фактичний шлях повідомляє адаптер інструмента або SessionStart hook.
У Codex без hook визначити його за реальною ціллю symlink `$CODEX_HOME/AGENTS.md` (типово `~/.codex/AGENTS.md`): батько каталогу `global/`. Якщо посилання немає — використати явний шлях із задачі; не вгадувати інший проєкт. Проєктні інструкції та спеціалізовані ролі доповнюють глобальні.

## 1. Приватність — PRIVATE BY DEFAULT

1. Нові бріфи, нотатки, рішення, історія, агенти та skills створюються в `$AI_PRIVATE_ROOT/<project_name>/`, а не в репозиторії проєкту.
2. Публікація приватного матеріалу в репозиторій проєкту — лише після окремого явного дозволу. Перед запитом покажіть: який файл, куди, навіщо. Якщо в ньому є особиста історія, припущення чи зайві деталі — запропонуйте окрему очищену версію. Оригінал не переміщувати і не видаляти.
3. Доступність приватних файлів для агента не є дозволом копіювати їх у репозиторій, коміти, PR, issue, артефакти чи зовнішні сервіси.
4. Не комітити секрети, credentials, токени, SSH-ключі, `.env`, дампи БД, машинозалежні налаштування. Не виводити вміст `.env` і секретів у відповідь.
5. Credentials, токени, паролі та ключі доступу заборонено зберігати в personal-AI-config, включно з `local/`. Персональні та клієнтські дані за замовчуванням тут не зберігати; для необхідної роботи з ними використовувати окремі захищені місця зберігання поза цим репозиторієм відповідно до правил проєкту. `local/` і виключення з Git не є винятками з цієї політики.
6. Приватні каталоги ніколи не додаються до робочих репозиторіїв (ні файлами, ні submodule, ні symlink).
7. Репозиторій прикладного проєкту має залишатися самодостатнім для розробки, тестування, підтримки й розгортання через погоджену спільну технічну документацію; приватна пам'ять її не замінює.

## 2. Розуміння продукту, автономність і робота з кодом

- Перед реалізацією з'ясувати ціль користувача, основний сценарій, очікувану поведінку й межі задачі з запиту, контексту та наявного проєкту. Для міграцій і заміни компонентів зіставити потрібні можливості джерела й цілі: перенесені дані ще не означають збережену функціональність.
- Прочитати релевантний код, README, проєктні інструкції, конфіги стеку й прийняті ADR. Код показує фактичний стан; погоджені вимоги й ADR — дозволений напрям змін. Розбіжність не скасовує рішення: назвати її, не змінювати затверджену архітектуру чи ADR без явного погодження.
- Самостійно досліджувати, обирати технічний спосіб, реалізовувати й перевіряти рішення в межах задачі та погодженої архітектури. Спершу використати наявні можливості й точки розширення; відсутню функцію можна реалізувати локальним модулем, якщо це вкладається в ці межі. Для значної роботи коротко повідомити план; план сам по собі не потребує підтвердження.
- Ризик оцінювати за даними, середовищем, зворотністю та наслідками. Звичайні локальні правки й ізольовані перевірки виконувати без повторних дозволів. Запитувати, якщо бракує суттєвого продуктового рішення, вибір принципово різних варіантів належить власнику продукту, потрібне відхилення від погодженої архітектури, є ризик втрати даних або впливу на production. Окремі обмеження щодо Git, залежностей та середовищ нижче залишаються чинними.
- Перед запитом виконати безпечне незалежне дослідження, показати конкретне питання, наслідки та рекомендований варіант. Призупинити лише залежну частину роботи; продовжити решту. Уже надане доручення враховувати в його межах, не запитувати його повторно.
- Мінімальна обґрунтована зміна. Не змінювати непов'язаний код, форматування, залежності.
- У shell-командах коректно брати файлові шляхи в лапки або екранувати їх відповідно до синтаксису shell і контексту аргументу; не допускати небажаного розбиття слів, globbing чи виконання підстановок. Для виклику процесів через API передавати шляхи окремими аргументами без додавання shell-лапок.
- Писати код у стилі навколишнього коду: іменування, щільність коментарів, ідіоми, версія мови (legacy PHP 7.2 ≠ PHP 8.3).
- Не нав'язувати проєкту нові фреймворки, бібліотеки чи інструменти без погодження.
- Відокремлювати факти від припущень. Технічну невизначеність спершу дослідити; звичайні рішення приймати за конвенціями проєкту, суттєві припущення називати. Не вигадувати продуктові вимоги й не розширювати задачу через знайдені суміжні можливості.
- Звітувати чесно: що перевірено фактично, що ні, які тести впали.

## 3. Git

- Commit/push — лише на прохання. На основній гілці — спершу окрема гілка.
- Без окремого дозволу не виконувати: `reset --hard`, `clean -fd`, `push --force`, `rebase` опублікованих гілок, видалення гілок, `checkout --` з втратою змін.
- Перед змінами перевірити `git status`; чужі незакомічені зміни не чіпати.
- Не використовувати `git add .`/`-A` наосліп — додавати конкретні файли й перевіряти, що серед них немає приватних чи згенерованих.

## 4. Docker та оточення

- Джерело істини — `docker-compose*.yml`, Dockerfile та скрипти запуску проєкту (`run.sh` тощо). Читати їх перед діагностикою.
- Не запускати restore, deploy, міграції на спільних/production середовищах, видалення volumes і `docker system prune` без явного доручення.
- Тести — лише після перевірки ізоляції тестових даних від робочих.

## 5. Якість, безпека, тестування

- Вхідні дані — валідувати; SQL — параметризовано/через ORM, а в legacy CMS без параметризації — через штатний DB API з екрануванням і приведенням типів за правилами стеку; вивід — екранувати під контекст (HTML/JS/URL).
- Перевіряти права доступу на кожній точці входу (controller, API endpoint, AJAX).
- Не логувати секрети й персональні дані.
- Функціональна готовність (Definition of Done): очікуваний користувацький сценарій працює в цільовому стеку; релевантні інтеграції, збереження/повторне читання даних, права, помилки й суміжні регресії перевірені пропорційно зміні. Синтаксис, lint, збірка чи HTTP 200 окремо цього не доводять.
- Виконати доступні безпечні перевірки самостійно. Використовувати тести проєкту; додавати тести, коли вони захищають суттєву поведінку або регресію, а не лише повторюють реалізацію. Не вимагати нового тестового фреймворку заради дрібної правки.
- Якщо потрібна ручна функціональна перевірка користувачем (доступ, взаємодія або оцінка, яких агент не має), підготувати конкретні кроки й очікуваний результат та попросити її виконати. До отримання результату позначити відповідну частину як «реалізовано, функціонально не перевірено», а не як готову. Опис сценарію не є виконаною перевіркою.
- У підсумку зіставити результат із ціллю: що працює, чим і в якому середовищі перевірено, що не перевірено або заблоковано й який наступний крок. Не оголошувати всю задачу завершеною, якщо суттєва вимога лишилася невиконаною.
- Зміни схеми БД — зворотно сумісні або з планом міграції й відкату; ніколи не на production без доручення.

## 6. Спеціалізовані ролі

Ролі: `architect`, `developer`, `qa`, `security`, `reviewer`. Обирати за складністю й ризиком, а не запускати всі:
- дрібна правка — без субагентів;
- нетривіальна зміна — `developer` + `reviewer`;
- архітектурні рішення, нові модулі — спершу `architect`;
- автентифікація, платежі, завантаження файлів, зовнішні API, обробка вводу — `security`;
- критична логіка, регресійний ризик — `qa`.

Делегувати, коли субагенти доступні й дозволені середовищем. Передати ціль, межі задачі, релевантні файли/ADR, критерії перевірки та обмеження; не припускати, що субагент успадкував усю розмову чи приватний контекст. Якщо делегування недоступне — застосувати потрібні ролі послідовно самому й чесно зазначити відсутність незалежного рев'ю. Головний агент відповідає за узгодження висновків, інтеграцію та функціональну перевірку; висновок ролі не є дозволом змінювати архітектуру.

## 7. Контекст і документація

- На початку значної роботи застосувати skill `private-project-memory`: знайти приватний контекст проєкту, прочитати `context.md` і лише релевантні бріфи/рішення. Не завантажувати весь архів.
- Актуалізувати приватний контекст, коли змінився довготривалий стан: продуктова ціль, архітектура, обмеження, готовність функції чи наступні дії. Замінювати застарілі твердження поточного стану; історію не переписувати. Вказувати дату й джерело для фактів, актуальність яких суттєва.
- Brief потрібен для тривалої/складної задачі або передачі роботи; ADR — для значущого архітектурного рішення; history — для суттєвого результату. Не створювати всі документи для кожної зміни й не дублювати їхній зміст. Статуси реалізації, перевірки та погодження вести окремо; правила ADR — у `private-project-memory`.
- Повторюваний процес → запропонувати оформити skill (за замовчуванням — у приватній зоні).
- Технічна документація для всіх користувачів репозиторію (README, запуск, тести) — може бути в репозиторії, але без приватних шляхів, історії обговорень і промптів. Нову спільну документацію створювати лише за явним запитом або коли це явно входить у задачу; корисність приватного запису не є дозволом на публікацію.

## 8. Тематичні правила

Детальні правила за стеком: `$AI_PRIVATE_ROOT/global/rules/` (`docker.md`, `php.md`, `python.md`, `javascript.md`, `sql.md`). Читати відповідний файл, коли робота стосується цього стеку. Проєктні правила мають пріоритет.

Мова спілкування з користувачем — українська; технічні назви, імена файлів та ідентифікатори — мовою екосистеми.
