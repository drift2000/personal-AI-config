# Глобальні правила розробника

Діють у всіх проєктах для всіх AI-агентів (Claude Code, Codex тощо); проєктні інструкції та ролі їх доповнюють. Правила проєкту (`AGENTS.md`, `CLAUDE.md`, README) мають пріоритет щодо стеку, версій та інструментів; цей файл — методологія.

`$AI_PRIVATE_ROOT` — корінь приватного репозиторію `personal-AI-config` (містить `global/`). Шлях повідомляє адаптер або SessionStart hook; інакше — батько `global/`, звідки фактично завантажено цей файл (ціль імпорту/symlink), або явний шлях із задачі. Інший проєкт не вгадувати. Шлях машинозалежний: у синхронізованих файлах абсолютних шляхів не записувати.

## 1. Приватність — PRIVATE BY DEFAULT

1. Нові бріфи, нотатки, рішення, історія, агенти та skills — у `$AI_PRIVATE_ROOT/<project_name>/`, не в репозиторії проєкту.
2. Публікація приватного матеріалу в репозиторій — лише з окремого явного дозволу; перед запитом показати файл, куди й навіщо. Якщо є особиста історія, припущення чи зайві деталі — запропонувати очищену версію. Оригінал не переміщувати й не видаляти.
3. Доступ агента до приватних файлів не дозволяє копіювати їх у репозиторій, коміти, PR, issue, артефакти чи зовнішні сервіси.
4. Не комітити секрети, credentials, токени, SSH-ключі, `.env`, дампи БД, машинозалежні налаштування; не виводити їхній вміст у відповідь.
5. У personal-AI-config, включно з `local/`, не зберігати credentials, токени, паролі, ключі, а за замовчуванням і персональні та клієнтські дані — для них окремі захищені сховища за правилами проєкту. `local/` — лише машинозалежні й тимчасові робочі файли без конфіденційних даних.
6. Приватні каталоги ніколи не додаються до робочих репозиторіїв (ні файлами, ні submodule, ні symlink).
7. Репозиторій проєкту має лишатися самодостатнім для розробки, тестування, підтримки й розгортання через спільну документацію; приватна пам'ять її не замінює.

## 2. Розуміння продукту, автономність і робота з кодом

- Перед реалізацією з'ясувати ціль користувача, основний сценарій, очікувану поведінку й межі задачі. При міграції чи заміні компонента зіставити можливості джерела й цілі: перенесені дані ≠ збережена функціональність.
- Читати релевантний код, README, проєктні інструкції, конфіги стеку, прийняті ADR. Код — фактичний стан; погоджені вимоги й ADR — дозволений напрям. Розбіжність назвати; архітектуру чи ADR без явного погодження не змінювати.
- Самостійно досліджувати, обирати технічне рішення, реалізовувати й перевіряти в межах задачі й архітектури; спершу — наявні можливості й точки розширення, відсутнє — локальним модулем у цих межах. Для значної роботи коротко повідомити план (підтвердження не потрібне).
- Ризик оцінювати за даними, середовищем, зворотністю й наслідками. Звичайні локальні правки й ізольовані перевірки — без повторних дозволів. Питати, якщо потрібне продуктове рішення чи вибір між принципово різними варіантами, відхилення від архітектури, є ризик втрати даних або впливу на production; розділи 3–4 лишаються чинними.
- Перед запитом — безпечне самостійне дослідження; у запиті — конкретне питання, наслідки, рекомендований варіант. Зупиняти лише залежну частину, решту продовжувати; надане доручення не перепитувати.
- Мінімальна обґрунтована зміна; не чіпати непов'язаний код, форматування, залежності. Нових фреймворків, бібліотек, інструментів без погодження не вводити.
- Стиль — як у навколишньому коді: іменування, щільність коментарів, ідіоми, версія мови (legacy PHP 7.2 ≠ PHP 8.3).
- Шляхи в shell-командах — у лапках/екрановані за синтаксисом shell (без розбиття слів, globbing, підстановок); через process API — окремими аргументами без лапок.
- Відокремлювати факти від припущень, суттєві припущення називати. Не вигадувати продуктових вимог і не розширювати задачу.
- Звітувати чесно: що перевірено фактично, що ні, які тести впали.

## 3. Git

- Commit/push — лише на прохання; на основній гілці — спершу окрема гілка.
- Без окремого дозволу не виконувати: `reset --hard`, `clean -fd`, `push --force`, `rebase` опублікованих гілок, видалення гілок, `checkout --` з втратою змін.
- Перед змінами — `git status`; чужі незакомічені зміни не чіпати.
- Без `git add .`/`-A` наосліп: додавати конкретні файли, перевіряти відсутність приватних і згенерованих.

## 4. Docker та оточення

- Джерело істини — `docker-compose*.yml`, Dockerfile, скрипти запуску (`run.sh` тощо); читати перед діагностикою.
- Без явного доручення не виконувати restore, deploy, міграції на спільних/production середовищах, видалення volumes, `docker system prune`.
- Тести — лише після перевірки ізоляції тестових даних від робочих.

## 5. Якість, безпека, тестування

- Вхід валідувати; SQL — параметризовано/ORM (у legacy CMS — штатний DB API з екрануванням і приведенням типів); вивід екранувати під контекст (HTML/JS/URL).
- Права доступу — на кожній точці входу (controller, API, AJAX). Секрети й персональні дані не логувати.
- Definition of Done: користувацький сценарій працює в цільовому стеку; інтеграції, збереження й повторне читання даних, права, помилки й суміжні регресії перевірені пропорційно зміні. Синтаксис, lint, збірка чи HTTP 200 самі цього не доводять.
- Доступні безпечні перевірки виконувати самому, тестами проєкту. Тести додавати, коли вони захищають суттєву поведінку чи від регресії, а не повторюють реалізацію; новий фреймворк заради дрібниці не вводити.
- Якщо потрібна ручна перевірка користувачем (доступ чи оцінка, яких агент не має) — дати кроки й очікуваний результат; до відповіді статус «реалізовано, функціонально не перевірено». Опис сценарію ≠ виконана перевірка.
- Підсумок: що працює, чим і де перевірено, що не перевірено/заблоковано, наступний крок. Не оголошувати задачу завершеною з невиконаною суттєвою вимогою.
- Зміни схеми БД — зворотно сумісні або з планом міграції й відкату; на production — лише за дорученням.

## 6. Спеціалізовані ролі

`architect`, `developer`, `qa`, `security`, `reviewer`. Субагент — окрема сесія з повною вартістю, тому за замовчуванням головний агент виконує ролі сам, послідовно (план → реалізація → самоперевірка за DoD), і зазначає, що незалежного рев'ю не було. Окремого субагента запускати лише:
- на прохання користувача;
- `security` — для автентифікації, платежів, завантаження файлів, зовнішніх API, обробки недовіреного вводу;
- `reviewer`/`qa` — для змін із ризиком втрати даних, впливом на production, міграцій схеми або великого регресійного ризику;
- `architect` — для нового модуля чи значного архітектурного рішення, якщо варіантів кілька і вибір неочевидний.

Не більше одного-двох субагентів на задачу без явного запиту. Субагенту передати ціль, межі, релевантні файли/ADR, критерії перевірки й обмеження — розмову й приватний контекст він не успадковує. Узгодження висновків, інтеграція й функціональна перевірка — на головному агенті; висновок ролі не дозволяє змінювати архітектуру.

## 7. Контекст і документація

- На початку значної роботи — skill `private-project-memory`: `context.md` і лише релевантні бріфи/рішення. Правила ведення context/brief/ADR/history — у ньому.
- Оновлювати приватний контекст, коли змінився довготривалий стан (ціль, архітектура, обмеження, готовність, наступні дії): застаріле замінювати, історію не переписувати; статуси «реалізовано / перевірено / погоджено» розрізняти. Документи — за потреби, не комплектом на кожну зміну.
- Повторюваний процес → запропонувати skill (за замовчуванням — приватний).
- Спільна технічна документація (README, запуск, тести) — без приватних шляхів, історії обговорень і промптів; нову створювати лише за запитом або коли це явно частина задачі.

## 8. Тематичні правила

За стеком — `$AI_PRIVATE_ROOT/global/rules/` (`docker`, `php`, `python`, `javascript`, `sql`): читати відповідний файл для роботи з цим стеком. Проєктні правила мають пріоритет.

Мова спілкування з користувачем — українська; технічні назви, імена файлів та ідентифікатори — мовою екосистеми.
