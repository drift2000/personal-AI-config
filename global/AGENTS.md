# Глобальні правила розробника

Ці правила діють у всіх проєктах і для всіх AI-агентів (Claude Code, Codex та інших).
Правила конкретного проєкту (`AGENTS.md`, `CLAUDE.md`, README у репозиторії) мають пріоритет щодо стеку, версій та інструментів. Цей файл — методологія, а не технологічні рішення.

`$AI_PRIVATE_ROOT` — корінь приватного репозиторію `personal-AI-config` (каталог, що містить `global/`). Фактичний шлях повідомляє адаптер інструмента або SessionStart hook.

## 1. Приватність — PRIVATE BY DEFAULT

1. Нові бріфи, нотатки, рішення, історія, агенти та skills створюються в `$AI_PRIVATE_ROOT/<project_name>/`, а не в репозиторії проєкту.
2. Публікація приватного матеріалу в репозиторій проєкту — лише після окремого явного дозволу. Перед запитом покажіть: який файл, куди, навіщо. Якщо в ньому є особиста історія, припущення чи зайві деталі — запропонуйте окрему очищену версію. Оригінал не переміщувати і не видаляти.
3. Доступність приватних файлів для агента не є дозволом копіювати їх у репозиторій, коміти, PR, issue, артефакти чи зовнішні сервіси.
4. Не комітити секрети, credentials, токени, SSH-ключі, `.env`, дампи БД, машинозалежні налаштування. Не виводити вміст `.env` і секретів у відповідь.
5. Приватний Git-репозиторій не дозволяє зберігати будь-які дані клієнтів. Сирі клієнтські дані — у `<project>/local/` (не синхронізується) або взагалі поза репозиторієм.
6. Приватні каталоги ніколи не додаються до робочих репозиторіїв (ні файлами, ні submodule, ні symlink).

## 2. Робота з кодом

- Спершу прочитати релевантний код, README і проєктні інструкції; реальний стан коду важливіший за документацію. Розбіжності — повідомити.
- Мінімальна обґрунтована зміна. Не змінювати непов'язаний код, форматування, залежності.
- Писати код у стилі навколишнього коду: іменування, щільність коментарів, ідіоми, версія мови (legacy PHP 7.2 ≠ PHP 8.3).
- Не нав'язувати проєкту нові фреймворки, бібліотеки чи інструменти без погодження.
- Відокремлювати факти від припущень. Неоднозначність, що впливає на реалізацію, — уточнити; дрібні рішення — прийняти за конвенцією і назвати.
- Звітувати чесно: що перевірено фактично, що ні, які тести впали.

## 3. Git

- Commit/push — лише на прохання. На основній гілці — спершу окрема гілка.
- Без окремого дозволу не виконувати: `reset --hard`, `clean -fd`, `push --force`, `rebase` опублікованих гілок, видалення гілок, `checkout --` з втратою змін.
- Перед змінами перевірити `git status`; чужі незакомічені зміни не чіпати.
- Не використовувати `git add .`/`-A` наосліп — додавати конкретні файли й перевіряти, що серед них немає приватних чи згенерованих.

## 4. Docker та оточення

- Джерело істини — `docker-compose*.yml`, Dockerfile та скрипти запуску проєкту (`run.sh` тощо). Читати їх перед діагностикою.
- Не запускати restore, deploy, міграції на спільних/production середовищах, видалення volumes і `docker system prune` без явного доручення.
- Тести — лише після перевірки ізоляції тестових даних від робочих.

## 5. Якість, безпека, тестування

- Вхідні дані — валідувати; SQL — лише параметризовано/через ORM; вивід — екранувати під контекст (HTML/JS/URL).
- Перевіряти права доступу на кожній точці входу (controller, API endpoint, AJAX).
- Не логувати секрети й персональні дані.
- Зміна поведінки → тест або чітко описаний ручний сценарій перевірки. Регресії перевіряти на суміжній функціональності.
- Зміни схеми БД — зворотно сумісні або з планом міграції й відкату; ніколи не на production без доручення.

## 6. Спеціалізовані ролі

Ролі: `architect`, `developer`, `qa`, `security`, `reviewer`. Обирати за складністю й ризиком, а не запускати всі:
- дрібна правка — без субагентів;
- нетривіальна зміна — `developer` + `reviewer`;
- архітектурні рішення, нові модулі — спершу `architect`;
- автентифікація, платежі, завантаження файлів, зовнішні API, обробка вводу — `security`;
- критична логіка, регресійний ризик — `qa`.

## 7. Контекст і документація

- На початку значної роботи застосувати skill `private-project-memory`: знайти приватний контекст проєкту, прочитати `context.md` і лише релевантні бріфи/рішення. Не завантажувати весь архів.
- Фіксувати важливі вимоги, рішення, результати й відкриті питання; не документувати кожну дрібну операцію і не переписувати історичні рішення заднім числом.
- Повторюваний процес → запропонувати оформити skill (за замовчуванням — у приватній зоні).
- Технічна документація для всіх користувачів репозиторію (README, запуск, тести) — може бути в репозиторії, але без приватних шляхів, історії обговорень і промптів.

## 8. Тематичні правила

Детальні правила за стеком: `$AI_PRIVATE_ROOT/global/rules/` (`docker.md`, `php.md`, `python.md`, `javascript.md`, `sql.md`). Читати відповідний файл, коли робота стосується цього стеку. Проєктні правила мають пріоритет.

Мова спілкування з користувачем — українська; технічні назви, імена файлів та ідентифікатори — мовою екосистеми.
