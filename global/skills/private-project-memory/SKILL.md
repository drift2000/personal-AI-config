# Приватна база знань проєкту

## Де лежить

`$AI_PRIVATE_ROOT/<project_name>/`, де `<project_name>` — ім'я кореневого каталогу проєкту (конвенція `<parent>/.private/<project_name>/`). Шлях і перелік наявних матеріалів зазвичай повідомляє SessionStart hook на початку сесії. Якщо hook відсутній або не визначив проєкт, використати явний шлях із задачі та перевірити корінь через `git rev-parse --show-toplevel`; для не-Git проєкту — явно заданий корінь. Спитати лише якщо після цього лишилася неоднозначність; не підставляти контекст іншого проєкту за активною вкладкою IDE.

```
<project_name>/
├─ context.md     # актуальний стан: що є, обмеження, ризики, посилання
├─ briefs/        # тематичні бріфи задач: YYYY-MM-DD-<topic>.md
├─ decisions/     # ADR: NNNN-<topic>.md (Status/Date/Context/Decision/Consequences)
├─ history/       # датовані факти виконаної роботи: YYYY-MM-DD.md
├─ skills/        # приватні проєктні skills (<name>/SKILL.md); legacy: .agents/skills/
├─ agents/        # приватні проєктні агенти (<role>.md)
├─ archive/       # застаріле/завершене — без змін вмісту
└─ local/         # НЕ синхронізується (gitignored); політика приватності діє
```

Шаблони: `templates/` поруч із цим файлом.

## На початку значної роботи

1. Визначити проєкт і приватний каталог (дані hook або шлях вище).
2. Прочитати `context.md`. Далі — лише бріфи/рішення, релевантні поточній задачі (за назвою файлу, посиланнями в context.md). Не читати весь архів і всю історію.
3. Визначити продуктову ціль, потрібний сценарій і поточний етап; звірити релевантні твердження з README, конфігами, кодом і перевірками. Відокремити фактичний стан від погодженого напряму (прийняті ADR). Назвати розбіжності; історичний запис, код або рекомендація агента самі по собі не скасовують погодження.
4. Якщо приватного каталогу немає і робота значна — запропонувати створити його з шаблонів (без запиту на дрібних задачах не створювати).

## Під час обговорення

- Відокремлювати факти (перевірено в коді/даних) від припущень.
- Технічну невизначеність досліджувати самостійно; рішення користувача запитувати за межами автономності з розділу 2 глобальних правил.
- Не записувати кожне повідомлення. Фіксувати тільки: погоджені вимоги, обмеження, рішення з обґрунтуванням, результати, відкриті питання.

## Після суттєвого етапу

Суттєвий етап — завершена фіча/дослідження, прийняте архітектурне рішення, змінений спосіб запуску чи обмеження. Не суттєво: окремий фікс, перейменування, форматування, проміжні кроки.

1. Оновити `context.md`, якщо змінився довготривалий стан: ціль/етап, архітектура, обмеження, перевірена готовність або наступні дії. Замінити застарілі твердження; для мінливих фактів вказати дату перевірки й джерело. Поточний контекст — коротка точка входу, не журнал і не копія звіту.
2. Значуще архітектурне рішення → `decisions/NNNN-*.md` зі `Status: proposed`, доки немає явного погодження; вже погоджене рішення можна одразу записати як `accepted` із датою й короткою вказівкою підстави погодження, без копії розмови. Прийнятий ADR, включно зі статусом, не змінювати без явного погодження. Для погодженої заміни створити новий `accepted` ADR з `Supersedes: NNNN`, у старому змінити лише статус на `superseded by MMMM`. До погодження старе рішення лишається чинним; опис реалізації, що відхилилася, не є його заміною.
3. Помітна виконана робота → короткі факти в `history/YYYY-MM-DD.md`: результат, перевірки, залишкові прогалини й посилання. Не дублювати brief/ADR; дрібна самодостатня зміна не потребує запису.
4. Brief створювати/оновлювати, коли задача складна, триває кілька етапів або потребує передачі роботи. Відкриті питання, неперевірені сценарії й наступні дії тримати в ньому або `context.md`, з посиланням з іншого документа. Не вимагати комплект context + brief + ADR + history для кожної зміни.
5. Коротко повідомити користувачу, що саме оновлено.

Оновлення в межах цієї приватної структури дозволені без окремого запиту, якщо вони відповідають правилам вище; це не дозвіл змінювати прийняті ADR. Видаляти чи переміщувати наявні приватні файли — лише на прохання; погоджене архівування — у `archive/` без зміни історичного вмісту.

## Публікація у спільний репозиторій

Завжди потребує окремого явного дозволу. Порядок:
1. Показати: який приватний файл, куди в репозиторії, з якою метою.
2. Якщо є особиста історія, припущення, приватні шляхи, промпти чи клієнтські деталі — запропонувати окрему очищену версію.
3. Створити спільну версію лише після дозволу; приватний оригінал не переміщувати й не видаляти.
4. Не додавати приватні каталоги в робочий репозиторій ні в якій формі.

## Нові приватні skills та агенти

- Повторюваний процес у проєкті → запропонувати skill у `<project>/skills/<name>/SKILL.md` (frontmatter лише `name` і `description` — сумісно з Claude Code і Codex). Не дублювати в ньому правила цього skill — посилатися на `private-project-memory`.
- Універсальний процес для багатьох проєктів → запропонувати skill у `$AI_PRIVATE_ROOT/global/skills/` (після створення — запустити `adapters/install.py`).
- Приватний агент → `<project>/agents/<role>.md` у форматі агентів Claude Code. Claude Code не реєструє його автоматично: щоб використати, запустіть субагента загального призначення і передайте йому тіло файлу ролі як інструкцію.

## Чого не робити

- Застосовувати розділ 1 глобальних правил до всього приватного workspace, включно з `local/`; не використовувати його як сховище конфіденційних даних. Для shell-команд застосовувати правило quoting шляхів із розділу 2.
- Не зберігати повні AI-розмови або приховані міркування. Відновлені матеріали зберігати без зміни історичного вмісту та позначати як історичні/неперевірені, доки факти не звірено.
- Не передавати приватні матеріали у зовнішні сервіси, артефакти, PR, issue.
